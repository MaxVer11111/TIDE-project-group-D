# 复现与演示指南

## 本地内容验证与mock

在PowerShell进入本交付文件夹。首次重建使用Python 3.13与官方PyPI；已有`.venv`可直接运行。

```powershell
python -m venv .venv
& ./.venv/Scripts/python.exe -m pip install --index-url https://pypi.org/simple -r requirements.lock.txt
& ./.venv/Scripts/python.exe src/run_validation.py
& ./.venv/Scripts/python.exe src/run_mock.py
& ./.venv/Scripts/python.exe src/build_itb_suite.py
```

依赖源场景文件夹必须与D组交付物保持同级。run_validation每次将原材料刷新至inputs并新建UTC时间证据目录，不覆盖旧轮次。预期内容20/20，mock26/26，进程exit code为0。数据检查打印两份CSV各2400条及清单hash匹配。源数据改变后应检查新报告，不能强行沿用旧摘要。

`证据/latest-validation.json`和`latest-mock.json`指出最新运行。每轮包含实际结果，JSON适合程序读取、Markdown适合查看；SHACL保留TTL和TXT原生输出。首次失败记录仍留存用于定位，不应只挑成功截图。

## ITB部署

```powershell
docker desktop start
docker compose -f ITB/compose.yaml up -d --build
docker compose -f ITB/compose.yaml ps
```

打开 http://localhost:19000 。首次admin@itb口令在本任务gitb-ui启动日志中查看，由用户完成初次改密，勿复制口令到分享文档。完成初始化后：建立TIDE测试domain/specification及community、organisation、system；向specification导入ITB/TIDE_D_W1W4.zip；给system建立TIDEProvider符合性声明，执行8例。导入报错要保留原报告并修复，不能只凭XML可解析判断TDL有效。

每例保留原生Session ID、步骤报告和输入/规则。负向用例除了invert后的成功，还要确认拒绝原因分别为rights_holder、source、access_level、script/窗口或records；错误解析/服务失败不能代替这些断言。P4_VALID_FIXTURE只表示结构验证，不称为真实Benchmark结果。

Suite 1.0.1的Recipe两例依赖validator-bridge容器：其真实执行jsonschema 4.26.0，不预置“通过”响应，不执行script。ITB通过HTTP调用再检查错误原因，绕过已观察到的内置JsonValidator位置报告异常。不要停掉该容器后把连接错误视为负例通过。

也可运行 `& ./.venv/Scripts/python.exe src/run_itb.py`。程序安全提示输入本机Master API key（从本机System administration的REST API项取得），或从进程环境变量TIDE_ITB_MASTER_KEY读取；不会保存key到报告。每次创建独立、带时间戳的实验配置，不覆盖历史。网络限制环境需允许访问本机19000。输出原生Session、XML报告与脱敏API记录到新证据目录。

查看容器时避免把包含首次口令的完整日志分享。停止本任务环境（保留卷与证据）：

```powershell
docker compose -f ITB/compose.yaml stop
```

恢复：`docker compose -f ITB/compose.yaml start`。本说明不要求删卷或重置其他Docker项目。基础镜像可按证据的RepoDigest锁定；当前ui/srv标签已固定1.30.3。

## 5–8分钟阶段演示

1. 打开README，说明“真实内容验证 + 明确mock业务状态”，没有真实VC/EDC。
2. 查看P1原输入及rules，运行run_validation，展示合法P1通过与缺rights_holder的focus node/path/message。
3. 展示非法Recipe和P4 records泄漏被准确拒绝，解释负向用例PASS。
4. 运行run_mock，展示“无Grant→自批失败→owner模拟批准→允许→收回拒绝”，以及更换metadata后旧报告失效。
5. 查看原生ITB状态说明；只有真实生成的Session才能作为ITB执行证据。TDL包本身是可编辑编排产物。
6. 打开TC矩阵和缺口清单，说明后续A/B/C交接。
